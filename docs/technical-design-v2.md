# MTG Travel Tabletop — Technical Design v2 (TypeScript + Vite)

Nov 2, 2026 · @Lawrence Tsang

## Status and scope

**Status: target design, not built yet.** v2 replaces v1 in place: the app isn't in production, so there is no migration period and no parallel deployment. Until v2 ships, the running app follows the [Technical Design v1](./technical-design-v1.md) (plain JavaScript, no bundler). From then on, this doc is the only technical design, and every later change is recorded here.

This doc describes how v2 is built, in enough detail to rebuild the app from it together with the [PRD](./prd.md), which does not change: v2 is a rewrite of the code, not of the product. Build order and testing live in the [implementation plan](./implementation-plan.md).

**What changes:** the language (strict TypeScript), the build (Vite), screen templates (TSX instead of htm strings), the service worker (generated by vite-plugin-pwa with content-hashed files), dependencies (npm instead of hand-vendored files), deployment (a GitHub Actions build), and browser tests (moved into the repo and run in CI).

**What carries over unchanged:** the game state schema, every engine rule and invariant, the host, the sessions, the WebRTC transport and pairing codes, the wire protocol, the IndexedDB schema, deck import, backup files and the action log. They are restated in full below so this doc stands alone. Nothing saved by v1 carries over: each device starts fresh with v2. The formats stay the same anyway, because nothing in v2 needs them changed, and because recordings made with v1 then serve as regression fixtures for the port.

**Governing constraint, unchanged: the engine is pure.** All game logic is a function `apply(state, command) → { state, moved } | { error, detail }` with no I/O, clock or randomness of its own.

## Architecture and modules

The layering is v1's. Commands flow toward the host, which applies them in order through the engine, saves, and sends the full state back to the guest over the WebRTC data channel; on one device the UI's LocalSession calls the host directly.

| Module | Files (`src/`) | Owns |
| --- | --- | --- |
| `engine/` | `engine.ts`, `view.ts` | State shape, `apply`, invariant passes and `checkInvariants`; zone helpers and visibility (`canSeeFace`, `visibleTo`) |

**Dependency rules,** enforced by a lint rule (`import-x/no-restricted-paths`, with `no-restricted-globals` keeping browser APIs out of `engine/`): `ui → client → host → engine`, and `ui`, `host`, `client` → `storage`. `engine/` imports only `engine/` and `types/`, and nothing in it may touch the DOM, IndexedDB, `crypto`, timers or `Date`. Every module may import `types/`.

## Offline, service worker and updates

The service worker is built by `vite-plugin-pwa` with `strategies: 'injectManifest'`: the plugin computes the precache list from the build and injects it into a small worker we write (`src/sw.ts`), so its behaviour is spelled out in our own code.

**Plugin options:** `registerType: 'prompt'`, `filename: 'sw.js'` (served at the root of the base path, so its scope covers the whole app), `injectManifest.globPatterns: ['**/*.{js,css,html,svg,png}']`, and `manifest` with v1's fields: name "Travel Tabletop", short\_name "Tabletop", `start_url` and `scope` `./`, `display: 'standalone'`, `orientation: 'any'`, background and theme colour `#0d1a15`, the three icons (the maskable one with `purpose: 'maskable'`).

**`src/sw.ts`**

1. `precacheAndRoute(self.__WB_MANIFEST)`: every built file, each with a revision, so the worker always fetches the exact version it lists and a stale browser-cache copy can't be mixed in. Changed JS and CSS also get new hashed names.
2. `cleanupOutdatedCaches()` on activate, which removes precaches left by earlier builds.
3. A `NavigationRoute` answering every navigation with the precached `index.html`, so game links (`#game=…`) open offline.
4. No runtime caching: requests to `api.scryfall.com` and the image CDN go straight to the network, as before.
5. On `message`, call `self.skipWaiting()` for `{ type: 'SKIP_WAITING' }` (sent by the plugin's register helper).
6. `clientsClaim()` on activate.

**Page side** (`main.tsx`). `registerSW({ onNeedRefresh, onOfflineReady })` from `virtual:pwa-register`. `onNeedRefresh` sets an app-wide "update ready" flag; calling the function `registerSW` returned activates the waiting worker and reloads. The flag shows **Update now** on the home screen only, as in v1; the game screen never offers it, so the game menu stays as it is. `onOfflineReady` shows a toast once, the first time the whole app is stored on the device: "Ready to play offline". `meta.offlineNoticeShown` records that it was shown, so it never repeats (a later update doesn't show it again).

**Build shown:** the home screen footer reads `Version <APP_VERSION> (build <BUILD_ID>)`, the commit the deploy was built from.

## Deploy

GitHub Pages serves the built `dist/` folder, deployed by a workflow instead of from the repository root.

- **One-time setting:** in the repository's Settings → Pages, set the source to **GitHub Actions** when v2 first goes live (step 4.2 of the plan). From then on the workflow builds and publishes `main` on every push. Between removing v1's code and that step, the site serves nothing.
- **`.github/workflows/deploy.yml`**, on every push to `main`: check out; set up Node (the version in `.nvmrc`); `npm ci`; `npm run typecheck`, `npm run lint`, `npm test`; `npm run build`; install Playwright's Chromium and run `npm run e2e` against `vite preview`; then upload `dist/` with `actions/upload-pages-artifact` and publish it with `actions/deploy-pages`. Any failing step stops the deploy, so a red build never reaches a device.
- **v1 code** is replaced in place on `main`; its last commit is tagged `v1` (`2d61e84`), so `git checkout v1` brings it back, and its design stays in the v1 doc.
- The site URL stays https://pikalaw.github.io/travel-tabletop/, so installed apps, bookmarks and game links keep working.

## Types

**`tsconfig.json`:** `strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `noImplicitOverride`, `noFallthroughCasesInSwitch`, `verbatimModuleSyntax`; `target` and `lib` ES2022 + DOM; `module: 'esnext'`, `moduleResolution: 'bundler'`; `jsx: 'react-jsx'` with `jsxImportSource: 'preact'`; `types: ['vite/client', 'vite-plugin-pwa/client']`. The worker (`src/sw.ts`) is checked with the `WebWorker` lib in its own small config.

**Shared types** (`src/types/`), the single source for every module:

- `state.ts`: `PlayerId`, `Actor`, `ZoneKind`, `ZoneId` (a template-literal type), `CardInstance`, `PlayerState`, `GameState`, exactly as in State schema below.
- `commands.ts`: `Command` is a discriminated union on `type`, one member per catalog entry, each with its own payload type, plus `NoticeCommand` and `UndoCommand`. `apply` switches on `cmd.type` and ends with an `assertNever` check, so adding a command without handling it fails the type check. `ApplyResult` is `{ state; moved } | { error: 'stale' | 'invalid'; detail? }`.
- `protocol.ts`: the message union (`hello`, `welcome`, `refuse`, `command`, `state`, `rejected`, `notice`) and the framing union (`msg`, `part`, `ping`).
- `storage.ts`: `CardDef`, `Deck`, `GameRecord`, `SnapshotRecord`, `LogEntry`, `BackupManifest`.

**Trust boundaries.** Anything from outside the app's own code arrives typed `unknown` and is narrowed by hand-written type guards before use: network messages (`net.ts`), backup files (`backup.ts`), Scryfall responses (`scryfall.ts`) and records read from IndexedDB that an older version may have written (`db.ts`). The engine still validates every command payload itself and returns `invalid` with a detail, because a guest's commands come over the network. A payload value may be any JSON, including an object whose `toString` is not a function, so the engine never passes one to `String()` or a template string: error messages format values with `str()`, and labels, names and ids must be strings. The host checks a notice's `zone`, `n`, `cardId` and `ids` before describing it. A property test sends every command and notice with random and hostile payloads through the host and requires that nothing throws.

**Component props** are typed interfaces, so a misspelled prop or a wrong argument to a component fails the build, which v1's htm templates could not catch.

## State schema

*Carried over unchanged from the v1 design (this and the next sections, through Action log); only file names gain `.ts`.* The types below live in `src/types/state.ts`. One serializable `GameState` object holds everything; zones are ordered arrays of card ids, and card instances hold everything else about a card.

```typescript
type PlayerId = 'p1' | 'p2';
type Actor = PlayerId | 'table' | 'host';
type ZoneKind = 'library' | 'hand' | 'battlefield' | 'lands' | 'graveyard' | 'exile' | 'command';
type ZoneId = `${PlayerId}.${ZoneKind}` | 'stack';

interface CardInstance {
  id: string;                 // 'c<n>' for deck cards, 't<n>' for tokens, unique per game
  defId: string;              // card definition in storage (images, name)
  name: string;
  deckId: string | null;      // null for tokens
  owner: PlayerId;            // player who selected the deck, or the token's owner
  isToken: boolean;
  tapped: boolean;
  face: 'front' | 'back';     // flip
  faceDown: boolean;          // hidden from everyone but the owner
  revealed: boolean;
  counters: { plus: number; minus: number; labeled: Record<string, number> };
  attachedTo?: string;        // host card id (same battlefield zone, one level)
  attacking?: number;         // attack number 1, 2, … while marked attacking
  blocking?: string[];        // ids of the attackers it blocks
  changed?: { by: PlayerId; turn: number }; // last changed in play, by whom and in which turn (protocol 4)
  ability?: { text: string; sourceId: string }; // an ability on the stack (id a<n>), and its source (protocol 5)
}

interface PlayerState {
  name: string;
  counters: { key: string; value: number }[];  // 'life' is always index 0
  libraryTopFaceUp: boolean;
}

interface GameState {
  schemaVersion: 1;
  gameId: string;
  mode: 'networked' | 'same-device';
  seq: number;                // incremented by every applied command
  turn: number;               // 0 before startGame, then 1, 2, …
  activePlayer: PlayerId;
  nextId: number;             // next numeric suffix for card and token ids
  players: Record<PlayerId, PlayerState>;
  cards: Record<string, CardInstance>;
  zones: Record<ZoneId, string[]>;  // index 0 = top of a pile / left of a row
  result: null | { winner: PlayerId | null; reason: 'concede' | 'ended' };
}
```

- **Zones.** 15 in all: seven kinds per player plus the shared `stack`. "Battlefield zones" are a player's `battlefield` and `lands`. A zone's owner (the part before the dot) is the player whose side it is on, which the app also treats as control.
- **Invariants** (`checkInvariants`, run by the property tests after every command): every card id is in exactly one zone; every zone entry exists in `cards`; the attachment and combat rules below hold.
- **Not in state:** viewer and perspective, open slots, sheets, the full view, the matchup highlight, pointer and combat modes. These are local UI state per device.
- **Card definitions** live in storage; the state carries `defId` and `name` only.

## Commands and engine rules

Every state change is a command the host applies through `apply`. A command names the zone the sender saw the card in; if the card is elsewhere, `apply` returns `{ error: 'stale' }`. Bad input returns `{ error: 'invalid', detail }`, where `detail` is a user-facing sentence for the combat checks. After a game ends (`result` set) only `startGame` is accepted.

```typescript
interface CommandEnvelope { type: string; actor: Actor; clientSeq?: number; payload: unknown; random?: number[]; }
```

**Catalog** (`STATE_COMMANDS`; each row is one member of the `Command` union)

| Command | Payload | Effect and preconditions |
| --- | --- | --- |
| `startGame` | gameId, mode, startingLife (default 20), deal (default 7), first, players: { p1, p2 } each { name, cards: \[{defId, name, deckId}\], commanders? } | Fresh state; card ids `c1…` in order; each library shuffled with host randomness; top `deal` to hand; commanders to the command zone; turn 1; activePlayer = `first` or p1 |
| `move` | cardId, from, to, toIndex? | See Moving cards |
| `tap` | cardId, from, value? | Sets `tapped` (toggles without value) |
| `untapAll` | player | Untaps that player's battlefield and lands |
| `flip` | cardId, from | Toggles `face` |
| `setFaceDown` | cardId, from, value? | Sets `faceDown` |
| `reveal` | cardId, from, value? | Sets `revealed` (kept for compatibility; the UI uses the `showCard` notice) |
| `addCounter` / `removeCounter` | cardId, from?, kind: plus, minus or label, label?, n? (default 1) | A label's count of 0 deletes it; removing below 0 is invalid |
| `createToken` | defId, name, to, toIndex?, owner? | New card `t<n>`, owner = given or the zone's owner |
| `removeToken` | cardId, from | Only tokens |
| `draw` / `mill` | player, n | Moves up to n from the library top: draw appends to hand, mill puts each on top of the graveyard; clears faceDown, revealed, tapped |
| `shuffle` | zone | Fisher–Yates over the zone with host randomness |
| `setLibraryTopFaceUp` | player, value |  |
| `setPlayerCounter` | player, key, value | Rounded to an integer |
| `addPlayerCounter` / `removePlayerCounter` | player, key, value? | Names unique (case-insensitive); `life` cannot be removed |
| `passTurn` | to? | activePlayer = to (default the other); turn + 1; untaps the new active player's battlefield and lands; clears combat marks |
| `concede` | player | result = { winner: other, reason: 'concede' } |
| `endGame` | winner? | result = { winner, reason: 'ended' } |
| `attach` / `detach` | see Attachments |  |
| `detachAll` | cardId (a host), from | Detaches every card attached to it, the same as detaching each in turn, nearest the host last; invalid if nothing is attached. Added in protocol 2 |
| `setLead` | cardId (an attached card), from | Makes it the group's lead (host): it swaps places with the old lead, the rest of the group attaches to it, and the old lead's `attacking` number, its `blocking` list and every block aimed at it move to the new lead; `tapped` and counters stay on their own cards; invalid on a card that is not attached. Added in protocol 3 |
| `attack` / `block` / `endCombat` | see Combat marks |  |
| `putAbility` | cardId (the source, in any zone), from, text | New item `a<n>` on top of the stack: `ability = { text, sourceId }` with the source's `defId` (its picture), name, deckId and owner, and face down if the source is. Text is trimmed; empty or over 2,000 characters is invalid. An item exists only on the stack: `move` to any other zone deletes it, and `attach` of an item is invalid. Added in protocol 5 |

`undo` is handled by the host, not the engine (see Host). Randomness: `randomNeeded(state, cmd)` returns how many numbers the host must supply (all deck cards for `startGame`, the zone size for `shuffle`, else 0); the engine reads them from `cmd.random`, clamped to \[0, 1).

**Moving cards** (`move`). The host card's attachments travel with it when it goes to a battlefield zone (see Attachments); an attached card that moves is detached. The moved cards are removed from `from`. A token whose destination is not a battlefield zone or the stack is deleted, and so is an ability item whose destination is not the stack. Otherwise each card passes through `changeZone(card, from, to)`:

- same zone: nothing changes;
- leaving the battlefield zones, entering them, or going to any non-battlefield zone: `tapped = false`;
- leaving the battlefield zones: counters cleared and `face = 'front'`;
- any zone change: `faceDown = false`, `revealed = false`.

They are inserted at `toIndex`, clamped to the destination's length; no index means the end. `moved` lists `{ id, from, to, toIndex }` for the log and ticker.

**Attachments.** `attach { cardId, from, toCardId, toZone }`: `toZone` must be a battlefield zone holding `toCardId`. If the target is itself attached, its host becomes the target (one level only). Attaching a card to itself, or to its own attachment, is invalid. A card that has attachments brings them along onto the new host. The group goes through `changeZone` into `toZone` and is inserted at the left end of the host's group, so the newest attachment is the farthest from the host (protocol 2 and earlier inserted it just before the host). An older log replays with a different attachment order; the order is only cosmetic. `detach { cardId, from }` clears the link and moves the card to just after its former host.

After every command `fixAttachments` restores these rules:

1. An attachment sits in its host's zone, which is a battlefield zone; otherwise its link is dropped. This is how a host leaving play frees its attachments where they lie.
2. Links are flattened to the bottom host, and a card that is a host cannot stay attached (this breaks any loop).
3. In every battlefield zone, each host's attachments come immediately before it, in their existing order. A card dropped inside a group therefore lands before that group.

**Combat marks.**

- `attack { cardId, from, value? }`: `from` must be a battlefield zone. Marking on requires `from`'s owner to be the active player; marking off is always allowed. A new attacker gets `attacking = (largest number in use) + 1`, so numbers never change under a blocker and restart once all marks are cleared.
- `block { cardId, from, attackerId, attackerZone, value? }`: both cards must be in battlefield zones, the attacker must be attacking, and a card cannot block itself. Adding a block requires `from`'s owner not to be the active player; removing is always allowed. It toggles `attackerId` in `blocking`, and an empty list is deleted.
- `endCombat` and `passTurn` delete every `attacking` and `blocking`.

`fixCombat` runs after every command, after `fixAttachments`. A card not in a battlefield zone loses both marks. A card off the active player's side loses `attacking`, and a card on the active player's side loses `blocking`, so a change of control removes a creature from combat. A blocker's references to cards no longer attacking are dropped.

**Changed marks.** `fixChanged` runs after `fixCombat`. A card out of play loses `changed`. On `passTurn` it drops marks with `turn < state.turn - 1`. A marking command (`move` except a reorder within one zone, `attach`, `detach`, `detachAll`, `setLead`, `tap`, `flip`, `setFaceDown`, `addCounter`, `removeCounter`, `createToken`, `attack`, `block`, `putAbility`) sets `changed = { by, turn }` on every card it touched (the payload's `cardId` and the moved cards) that is now in play; `by` is the actor, or the active player for `table`, and `host` marks nothing. When `by` is the active player, marks with `turn < state.turn` are dropped first. The untap in `passTurn`, `untapAll` and `endCombat` mark nothing. `checkInvariants` checks that only cards in play carry a mark and none is older than the previous turn, and that every ability item is on the stack. The v1 compatibility replay compares states without `changed`, a field v1 never had.

**Notices** are logged and broadcast but change no state: `peek` (zone, n), `revealTop` (zone, n, ids), `searchOpen` / `searchClose` (zone), `inspect` (zone), `point` (cardId? zone?), `showCard` (cardId, zone), `coinFlip`, `rollDie` (sides), `randomPick` (zone), `info`. The host fills results: coin `heads` / `tails`; die sides clamped to 2–1000 with result 1…sides; randomPick's `cardId` (an empty zone is invalid). A `searchClose` on a library is followed by a host-issued `shuffle`. Alert notices: peek, revealTop, searchOpen, searchClose, inspect, coinFlip, rollDie, randomPick.

## Visibility

`canSeeFace(state, card, zone, viewer)`, with `viewer` a player or `'nobody'` (one device, blinded):

- library: only the top card, and only when that library's `libraryTopFaceUp` is set;
- hand: when `revealed`, or when the viewer is the zone's owner;
- elsewhere: everyone, unless `faceDown`, in which case only the card's owner.

`visibleTo(state, card, zone)` is the players for whom that holds; the log records it before and after every move. Visibility is enforced only in the UI; both devices hold the full state, which the PRD accepts. The peek, search and inspect trays and the full-screen view of a face-down card you own override it for the viewer.

**Perspective and viewer.** Networked: both are the device's player. One device: unblinding sets both to that player; blinding sets the viewer to `'nobody'`, and while blinded the board is drawn from the active player's side (`P = viewer === 'nobody' ? state.activePlayer : persp`), so a pass turns it to the next player and undoing the pass turns it back, with no special case. A blinded table also acts for that player. The actor for commands is the viewer, or `'table'` when the viewer is `'nobody'`; the "acting player" is the viewer, or the perspective player when blinded.

## Host

`Host` (`host.ts`) owns the authoritative state. `dispatch(cmd)`:

1. `undo` → pop the snapshot stack; the popped state becomes current. Logged as `kind: 'undo'` with `undoneSeq`. Nothing to undo is invalid. Undo works after a game has ended too (it is handled before the engine's game-over check).
2. Notice types → fill results, log, emit `notice`.
3. State commands → fill `random` with `crypto.getRandomValues` (32-bit values ÷ 2³²), `apply`, and on error log a `rejected` entry and return `{ ok: false, error, detail }`.
4. On success: push the prior state as a snapshot (capped at 100; `startGame` clears the stack instead), bump `version`, describe the command for the ticker, and compute `alert` (a `shuffle`, a `move` out of a library, or anything into a library). Write a `command` log entry with per-card `visibleTo`, plus a `snapshot` entry after `startGame`, `passTurn`, `concede` and `endGame`. Persist, then emit `state` with { version, text, alert, actor, clientSeq }.

Persistence is serialized through one promise chain; each commit is one IndexedDB transaction (game record + snapshot push/drops + log entries). `replay(entries)` rebuilds the state from a log by applying the logged commands and undos in `seq` order.

**Ticker text** (`describe.ts`). Card names appear only if both players could see the card before or after; otherwise "a card" or "a token". Zones read "their battlefield" for the actor's own, "Claire's graveyard" otherwise, and "the top of" / "the bottom of" a library. Templates: `<who>: <card> → <zone>`, `<who> reordered <zone>`, `<who> tapped|untapped <card>`, `<who> untapped all`, `<who> flipped <card>`, `<who> turned a card face down|up`, `<who> added|removed a <kind> counter on|from <card>`, `<who> created <token>`, `<who> drew|milled <n> card(s)`, `<who> shuffled <zone>`, `<who>: <player> <key> <old> → <new>`, `<who> attached <card> to <host>`, `<who> detached <card>`, `<who>: <card> attacks (⚔n)`, `<who>: <card> blocks <attacker> (⚔n)`, `<who> ended combat`, `Turn <n>: <player>`, `<player> conceded`, `<who> undid the last action`. Notices: `<who> is looking at the top <n> of <zone>`, `revealed the top <n> of`, `is searching`, `finished searching`, `is looking at`, `is pointing`, `revealed <card>`, `flipped a coin: heads`, `rolled a d<s>: <r>`, `picked at random from <zone>`. `<who>` is the player's name, or "Table".

## Sessions, transport and protocol

**Sessions** share one interface for the UI: `state`, `version`, `status`, `subscribe(fn)`, `onNotice(fn)`, `onReject(fn)`, `send(type, payload, actor)`.

- `LocalSession` wraps a `Host`, for one device (`kind: 'same-device'`) or the networked host (`kind: 'host'`, me = p1, guest = p2). It forwards every `state` and `notice` to the attached guest transport; guest `command` messages are dispatched with actor p2, and failures are answered with `rejected`.
- `GuestSession` (`kind: 'guest'`) keeps the last state from the host. `send` posts `{ type: 'command', cmd: { type, payload, clientSeq } }`; while not connected it rejects locally with reason `offline`, and the board goes read-only. A `rejected` message triggers a re-render, so a card snaps back.

**Transport** (`webrtc.ts`). One ordered `RTCDataChannel` named `mtg`, `iceServers: []` (LAN only).

- **Pairing.** The host creates the channel and an offer; the guest answers. Each side waits for ICE gathering to complete (timeout 4 s; no trickle) so one code carries every candidate. Before creating a code, the app requests the camera once and stops it at once, because Safari and Chrome hide local IP addresses from WebRTC without camera access. The connection times out after 20 s, or fails at once on `connectionState = 'failed'`.
- **Codes** (`codec.ts`). `"MTG1" + ("o" | "a") + base64url(deflate(level 9, slimmed SDP))`. Slimming drops `a=extmap`, `a=rtcp-fb`, `a=ssrc` and `a=msid` lines and srflx, relay and TCP candidates. Decoding ignores whitespace and gives a readable error for a wrong or damaged code. QR codes are encoded with ECC level L and border 2, drawn as SVG. Scanning uses the rear camera at up to 1280 px wide, frames scaled to 800 px, jsQR with `inversionAttempts: 'dontInvert'`, accepting only text starting `MTG1`.
- **Framing.** Each message is JSON `{ t: 'msg', m }`. Text over 15,000 characters is split into `{ t: 'part', id, i, n, d }` chunks and reassembled. `{ t: 'ping' }` goes every 2 s; nothing received for 7 s marks the link `lost`, and traffic on an open channel marks it `open` again.

**Messages**

| Type | Direction | Contents |
| --- | --- | --- |
| `hello` | guest → host | protocolVersion, appVersion, name, spec { cards, commanders } from the chosen decks, deckNames, tokens (every token defId on the guest), gameId (when reconnecting) |
| `welcome` | host → guest | player ('p2'), state, version, tokens |
| `refuse` | either | reason: `version`, `cards` (with `missing` names), or `game`; detail |
| `command` | guest → host | cmd { type, payload, clientSeq } |
| `state` | host → guest | version, state, text, alert, actor, clientSeq (on the guest's own commands) |
| `rejected` | host → guest | clientSeq, reason, detail |
| `notice` | host → guest | the filled notice { kind, actor, payload, text, alert, seq } |

**Handshake.** The host refuses a different protocol or app version. For a new game it refuses a guest whose cards it lacks (by defId). If a game is running, a hello with that game's id reconnects, a hello with another id is refused (`game`), and a hello with no id starts a new game with the guest's name and spec. The host then sends `welcome` and the full state. The guest checks that it holds every non-token defId in the welcome's state; if not, it refuses and names the missing cards. The guest stores `guestGame` (gameId, host name, its own name and deck ids) for reconnecting.

## Storage

One IndexedDB database `mtg-tabletop`, version 2. Version 1 is v1's layout; version 2 adds the `rulings` store and card text. The upgrade deletes nothing. Cards imported before version 2 have no text; at startup the app names the imported decks that hold such cards (`staleDecks`) and asks the user to delete and re-import them: a lasting notice on the home screen, like the update notice, and a "needs re-import" tag on each such deck in the deck list. Both go away once those decks are deleted.

| Store | Key | Contents |
| --- | --- | --- |
| `images` | `hash` | { hash, blob, type }: SHA-256 hex of the bytes; each image stored once |
| `defs` | `id` | CardDef { id, name, front, back, scryfallId?, sizes?, text? }; `text` = { oracleId?, layout?, faces: [{ name, typeLine, oracleText, manaCost?, power?, toughness?, loyalty?, defense? }], record } |
| `decks` | `id` | Deck { id, name, kind: 'deck' or 'token', cards (defIds, with repeats), commanders?, builtin?, starterId?, forDecks?, signature?, createdAt } |
| `games` | `id` | { id, state, mode, role, setup, updatedAt, over } |
| `snapshots` | \[gameId, key\] | { gameId, key, state }; index `gameId` |
| `logs` | \[gameId, seq\] | LogEntry; index `gameId` |
| `rulings` | `oracleId` | { oracleId, rulings: [{ source, publishedAt, comment }], fetchedAt } |
| `meta` | `key` | `fixtures` (sample-deck version), `lastSetup` { names, pick, life }, `guestGame`, `offlineNoticeShown` (new in v2; an extra key, so v1 records still read) |

- **Card ids.** `defId = sha256("name|frontHash|backHash")`, first 20 hex characters (back hash empty when there is none). Identical imports produce identical ids on every device, which is what the handshake compares.
- **Images.** `front` and `back` are the normal-size hashes; `sizes.front` and `sizes.back` hold the small and large hashes. Single-faced cards have `back: null` and are drawn with the bundled `back.svg`. Missing sizes fall back to normal.
- **Choosing a size.** `sizeFor(cssHeight)`: with px = cssHeight × devicePixelRatio, small up to 230 px, normal up to 720 px, large above. The full-screen views always use large.
- **Games.** `games.over` is set when `state.result` is. Deleting a game deletes its snapshots and logs. Resuming loads the record, its snapshots (sorted by key) and the last log seq.
- **Cleanup sweep.** A card is stored once and shared by every deck and game that uses it, so deleting a deck or a game never deletes cards directly. `sweep()` runs after every import, restore, sample-deck rebuild, deck delete (one or many: `deleteDecks`, used by Delete all decks) and game delete. In one transaction it collects the card ids used by any deck, saved game or undo snapshot, then deletes every other card, every image no remaining card refers to (`hashesOf`: front, back and their sizes), and every rulings record no remaining card's oracle id names. A deck that is in a saved game can be deleted; its cards stay until the game is deleted too. Imports, restores and the sample decks store cards before the deck that uses them, so they run under `holdSweep`; a sweep asked for meanwhile waits until the last of them ends. If any record fails its type guard, the sweep deletes nothing.
- **Persistence request.** `navigator.storage.persist()` after decks are added; `persisted()` and `estimate()` feed the Decks screen's status line.

## Deck import

`importDeck({ name, kind, text, extra, tokens })` in `scryfall.ts`. It needs internet; nothing else does. Import also keeps each card's rules text and fetches its rulings once per unique card; see Stack and abilities.

1. **Parse** (`parseDecklist`). Skip blank lines and lines starting with `//` or `#`, and "Name …" lines. Section headers (an optional trailing colon): Commander(s) → commander; Deck / Main / Mainboard / Main deck → main; Sideboard, Maybeboard, Considering, Companion, Tokens, About → that section. A card line matches `^(\d+)\s*x?\s+(name)(\s+\((SET)\)(\s+number)?)?(\s+\*foil-tag\*)*$`, with a SET of 2–6 letters or digits. A line that doesn't match but starts with a letter is one copy of that name; anything else is an error. Main and commander lines are imported (and tokens-section lines for a token deck); the rest are ignored.
2. **Resolve.** Unique entries (keyed by set and number, or lower-cased name) go to `POST https://api.scryfall.com/cards/collection` in batches of 75. The identifier is { set, collector\_number }, { name, set }, or { name }. A result matches an entry by set and number, or by its name or a face's name (case-insensitive), or by a name starting with "\<name> //". Unmatched entries try `GET /cards/named?fuzzy=<name>`. Requests are 120 ms apart; a 429 retries after 1, 2 and 3 s; a 404 is "not found".
3. **Download.** Four at a time. A card already stored with all three sizes (by Scryfall id) is reused. Image URLs come from `image_uris`, or from `card_faces[0]` and `[1]` for double-faced cards; for each face the small (146×204), normal (488×680) and large (672×936) images are fetched, stored, and the CardDef written.
4. **Write the deck.** `deck-<base36 time>-<5 random base36>`, with `cards` and `commanders` expanded by count, `signature = listSignature(text)`, and `extra` merged (for example `starterId`).
5. **Tokens** (kind 'deck' only). Every `all_parts` entry with `component: 'token'` (except the card itself) is fetched through the collection endpoint by id and stored the same way. They go into token deck `tokens.deckId`, or `<deckId>-tokens` named "\<deck> · tokens". The cards are merged without duplicates, and the new deck's id is added to `forDecks`.
6. Unresolved lines and cards without images are returned as `missing`; the rest still imports.

`listSignature(text)` is the sorted list of "count name" (commanders prefixed `c:`) for duplicate warnings. The Import screen warns when a deck of the same kind has the same name (case-insensitive) or the same signature.

**Starter packs** (`starters.ts`). One pack, id `tla-beginner-box`, "Avatar: The Last Airbender Beginner Box". Its token deck is `tla-bb-tokens`, "Avatar BB: Tokens". It has ten decks; each line without a count gets "1 ", and every line gets " (TLA)". Each deck is named "Avatar BB: \<name>" with `starterId` `tla-bb-<name, lower-case, non-letters → '-'>`. The Decks screen imports only the decks whose `starterId` is missing. The lists are in the appendix.

**Sample decks** (`fixtures.ts`). Created once per fixture version (2, stored in `meta.fixtures`) as SVG cards drawn in code (630×880, a coloured frame, name, cost, art, type line, wrapped rules text, power/toughness box, and "Sample card · placeholder art"). The decks are `sample-ember` "Sample: Ember (red)", `sample-grove` "Sample: Grove (green)" and the token deck `builtin-tokens` "Basic tokens", all `builtin: true`. Contents are in the appendix.

## Backup files

`backup.ts`. A zip built with fflate, extension `.mtgdecks`, named `tabletop-decks-<YYYY-MM-DD>.mtgdecks`. v1 and v2 read each other's files.

- `manifest.json`: { format: `travel-tabletop-decks`, version: 1, exportedAt, decks, defs, images: { hash → extension }, rulings? }. `defs` carry each card's rules text; `rulings` holds the rulings record of every card in `defs` that has one, by oracle id. It is optional, so the format stays version 1: an app from before rulings were backed up ignores it, and a file without it restores without rulings.
- `images/<sha256>.<ext>`: each image every def refers to (both faces, all sizes), stored without recompression; extensions jpg, png, svg, webp from the MIME type.
- Token decks whose `forDecks` include a chosen deck are added automatically (never built-in ones).
- **Reading** compares each deck with the device: `same` when its id exists (`builtin` when that deck is built in here); `similar` when a deck of the same kind has the same name (case-insensitive), signature or `starterId`; otherwise `new`. The restore screen selects `new` and `same` rows, shows `same` as "Will update", and locks `builtin` rows. A wrong format is refused, and so is a newer `version`.
- **Restoring** the chosen decks writes only defs whose every image is present and matches its hash, and lists the cards skipped. It stores the rulings of the restored cards, unless the device has a copy fetched as recently. A deck whose id exists is replaced by the file's, keeping its id (no copies); a token deck is merged instead: the union of both copies' `cards` and `forDecks`. A built-in deck on the device is never restored over. Restored decks have `builtin` cleared. The result counts the decks restored and how many of them were updates.
- Files reach the user through `navigator.share({ files })` on touch devices (`pointer: coarse`) when sharing is supported, otherwise as a download. The file picker accepts any file, because iOS may not recognise the extension.

## Action log

Every host action writes log entries with a per-game increasing `seq`.

```typescript
interface LogEntry {
  gameId: string; seq: number; ts: string; mode: 'networked' | 'same-device'; turn: number;
  kind: 'command' | 'notice' | 'rejected' | 'undo' | 'snapshot';
  actor: Actor; schemaVersion: number;
  command?: Command;          // as applied, with random filled in
  notice?: Notice;            // as filled in by the host
  text?: string;              // the ticker text
  alert?: boolean;            // kind 'command': the ticker alert (library moves, shuffles)
  cards?: { id: string; defId: string; name: string; from?: ZoneId; to?: ZoneId; toIndex?: number;
            visibleTo: { before: PlayerId[]; after: PlayerId[] } }[];
  undoneSeq?: number;         // kind 'undo': the state seq that was reverted
  reason?: string;            // kind 'rejected'
  state?: GameState;          // kind 'snapshot'
}
```

**Recent actions after a resume.** The log sheet (tap the ticker) shows the last 200 lines. Live lines come from the session; when a saved game is resumed, `App` passes the stored log's lines in as `history` (`logLines` in `gameUi.ts`: commands, notices and undos with their text, alert and time), so the sheet and the ticker carry on where they were. They are tied to the resumed game's id, so a rematch starts with an empty sheet. A guest keeps no log, so a guest's sheet starts empty when it reconnects.

**Exporting the log.** One JSON Lines file `mtg-game-<gameId>.jsonl`: a manifest line { kind: 'manifest', gameId, mode, players, exportedAt, schemaVersion }, then every log entry. On one device it is refused before the game ends; on a guest it is refused.

## UI

**What changes from v1.** Screens are Preact function components in TSX with typed props, using `preact/hooks`; there are no htm templates. Styling stays one plain stylesheet, `src/styles.css`, with v1's class names, so the app looks the same and the browser tests can keep their selectors. The game screen's local state moves from a dozen separate `useState` flags into one `useReducer` with a typed `UiState`: the mutually exclusive modes (normal, combat with an optional pending blocker, attach, pointer, library footer) become one discriminated `mode` field, so two modes can never be on at once. Everything the player sees and does is as the PRD and the sections below describe.

**Shell** (`App.tsx`). On start: create the sample decks if needed, register the service worker (see Offline), then open the game link in the URL or the home screen. Routes: home, decks, deck, import, backup, restore, setup, rejoin, game. Toasts (`toast.ts`) show at the top, at most four at once, for 3.5 s by default; kinds are info, warn and big (dice).

**Dialogs** (`dialogs.ts`, `Dialogs.tsx`). The app never calls `window.confirm` or `window.prompt` (the browser names the site in them and blocks the page). `confirmBox({ title, body?, ok?, cancel?, danger? })` resolves true/false, `promptBox({ title, body?, value?, ok?, cancel?, numeric?, placeholder? })` resolves the text or null, and `copyBox({ title, body?, value })` shows read-only text to copy by hand (the pairing code when the clipboard fails). They queue in a module-level list; `<Dialogs/>`, mounted once at the app root, renders the front one in `.confirm-screen` / `.confirm-box.plain` (`.danger` makes the OK button red). On open it blurs the focused element and focuses the input (selected) or the OK button, and a window keydown listener (attached in a layout effect) maps Enter to OK and Escape to Cancel; a tap on the backdrop cancels. That tap counts only if the press also began on the backdrop (`useOutsideTap` in `hooks.ts`, also used by the unblind confirmation and the deck card viewer): on a touchscreen, the click that follows a tap lands on whatever is under the finger when it lifts, so a dialog opened by a tap (the labeled-counter chip, say) would otherwise close at once. Inputs use 16 px text so iOS doesn't zoom.

**Setup.** One device: two player forms (name and a deck checklist); start requires a deck each. Host: one form, then the host pairing flow. Join: one form, then the guest pairing flow. Starting life buttons 20 / 30 / 40 plus a number field. `lastSetup` is saved. Game ids come from `newGameId()`: the ISO date, "-", and 16 Crockford base32 characters (alphabet `0123456789abcdefghjkmnpqrstvwxyz`) from 10 random bytes.

**Game links** (`link.ts`). The game screen keeps `#game=<id>` in the address bar with `history.replaceState` and clears it on leaving. On startup and on `hashchange` (when no game is open), `#game=<id>` (id matching `[0-9A-Za-z-]{1,64}`) is resolved in order:

1. a saved game that isn't over and has `turn > 0` is resumed;
2. an id matching `meta.guestGame` opens the reconnect screen;
3. otherwise the home screen shows "That game has ended." (a record exists) or "That game isn't saved on this device…".

During a game, a changed hash is put back.

**Board** (`Board.tsx`). A CSS grid, 3 px gaps. Columns are `minmax(54px, 16%) 1fr minmax(54px, 16%)` (11% and 58 px in landscape). Rows are `minmax(43px, 0.55fr) 1.4fr 1.4fr minmax(43px, 0.55fr) 1fr`: equal battlefields get the most room, then the hand, then equal lands rows, whose 43 px floor keeps land cards tappable on a phone held sideways (the floor binds only there; measured row heights are 43 / 78 / 78 / 43 / 56 px on an 844×390 screen and 84 / 215 / 215 / 84 / 153 px on 390×844). Cells for perspective P and other player O:

| Row | Column 1 | Column 2 | Column 3 |
| --- | --- | --- | --- |
| 1 | O.exile | O.lands (+ "O: n in hand", right-aligned) | O.graveyard |
| 2 | O.command | O.battlefield | O.library |
| 3 | P.command | P.battlefield | P.library |
| 4 | P.exile | P.lands | P.graveyard |
| 5 | player counters | P.hand | stack |

Row zones are drawn by `Row`, piles by `Pile` (the top card, with a library split into Top and Bottom drop halves). The board's class is `my-turn` or `their-turn`. Its background is two layers, the board's `::before` and `::after`, placed as grid items behind the cells: one spans the opponent's two rows, the other this side's three, so the tint splits exactly where the players' rows meet at every screen size (the margins reach over the padding). The active player's half fades from red `rgba(214,64,52,.38)` at its outer edge to `.12` near the seam; the other half does the same in blue `rgba(60,110,220,…)`. At the seam each layer reaches 12 px past it and fades to transparent, so the colours cross-fade over 24 px centred on the gap. Cells are translucent, so the tint shows through. Every player name on the board (turn label, counters cell, opponent hand count, and the name in each row label, rendered by a `Who` component) is `--hot` `#ff7b5f` (class `role-atk`) for the active player and `--cool` `#7aa7ff` (`role-def`) for the other; the rest of each label stays grey.

A card in play with `changed` gets a `.changed-bar` (4 px, `--hot` when `changed.by` is the active player, else `--cool`) at the left of the `.card` frame. The frame never rotates (only `.card-inner` does), so on a tapped card the bar stays on the left, with `top` and `height` set to the turned picture's extent. **Pass turn** (footer and menu) shows only when the actor is the active player or `table`.

**Rows** (`Cards.tsx`). Card height = slot height − 14 px; width = height × 63/88 (a tapped card's box is square, and its image is rotated 90° clockwise, the paper convention).

- **Units.** Groups (a host and its attachments) are units. Inside a group, each later card overlaps the previous by 75% of its width (PEEK 0.25). Between units the gap is 4 px.
- **Collapsed.** If the natural width exceeds the slot width − 8 px and there is more than one unit, the row collapses, the overlap spread evenly between units, unless the slot is open.
- **Open.** The row scrolls sideways. If it holds groups, they fan out: 3 px inside a group, 14 px between groups.
- **Overlays.** The label and the open-slot outline sit outside the scroller so they don't scroll. Data attributes on the row (`data-collapsed`, `data-groups`, `data-fanned`) drive the tap logic. The row gets `can-open` (which shows "tap to open") when it is collapsed, or holds groups and isn't open; the open box shows "tap to close".

**Cards.** Each card element carries `data-card`, `data-zone`, `data-card-target` and `data-attached-to`. Marks sit at the visible top-left corner, outside the rotated image, offset down by (height − width) / 2 when tapped: "+N" attachments (gold); ⚔n attacking (red) and 🛡n per blocked attacker (blue), both draggable; T token, FD face down, R revealed, ↻ back face. Counter badges (+n, −n, label n) sit at the bottom centre, draggable, with an invisible 8 px margin for fingers. Tucked attachments hide their badges.

**Gestures** (`gestures.ts`). One handler on the game root, plain DOM code (not a component), typed.

- **Sources:** `[data-card]`, `[data-counter]` (footer tags), `[data-badge]` (marks and counters on cards), `[data-token-def]`, `[data-tap]`. **Drop targets:** `[data-drop]` (with `data-layout` row, pile, library, tray or append; `append` drops at the end, used by the "O: n in hand" label, which takes pointer events only while dragging), `[data-card-target]` for counters and tags, `[data-trash]` (the Tokens button).
- **Thresholds:** a movement over 8 px starts a drag; holding a card, or a token in the Tokens sheet, 480 ms is a long-press (with a 15 ms vibration). A two-finger spread on either opens it full screen too.
- **Scrollers:** the footer bar and open rows use `touch-action: none` and are panned in code. A mostly horizontal movement in a scroller pans it and swallows the next click for 400 ms; it ends with a fling that decays by 0.95 per 16 ms. Counter and mark drags never pan.
- **Drag:** a ghost copy follows the finger, and the hovered target is highlighted. An element with `data-drag-text` (an ability item on the stack, an ability line in the full view) drags as a 220 px box of that text instead of a copy of its picture, so an ability looks the same going onto the stack and coming off it. **Drops:** a counter onto a card target; anything else onto a slot. The row index is the number of cards whose centre is left of the drop point, excluding the dragged card and its attachments, plus the tray offset. A library drop goes to the top or bottom by half. A drop outside every target reports `nowhere`, with the card under the finger.
- **Taps** on a mark or counter on the board act on its card.

**Game screen** (`Game.tsx`). `UiState`: viewer, perspective, open slots (a list), `mode` (above, with the library zone and N for the library footer), sheet, full-view card `{ cardId, zone, anchor }`, the highlighted matchup's card id, reveal screen, confirm-player dialog, the label name; plus the art map, the log lines (last 200) and the pointer ring.

- **Tokens sheet:** `gameTokens(state, tokenDecks, art)` lists the definition ids of every token deck whose `forDecks` includes a deck in the game, each once, sorted by name; the sheet shows them as one grid. The built-in basic tokens are made for the two sample decks (fixture version 3). A long-press or spread on a token opens `CardViewer` (`CardViewer.tsx`, shared with the deck page) over the sheet, stepping through the same list; its drag up closes it and hands the sheet's element for that token to a board drag (`adopt`), as the full view does for a card.
- **Full-screen card frame** (`CardFrame.tsx`, with `cardGestures.ts`): the large picture, the ← and → signs (shown where `onPrev` or `onNext` is set), the arrow keys (ignored while typing in a field) and `useCardGestures({ onTap, onPrev, onNext, onDragOut, onClose })`: a tap, a sideways swipe (50 px), a drag up (40 px, handed off) and a swipe down (50 px). The pointer is captured on press, so a mouse swipe that ends past the card's edge still counts; it is released when a drag up hands off. `FullCard` and `CardViewer` both draw it, so the full view, the deck page and the token viewer look and swipe alike; only the callbacks and what each screen draws around the frame differ (the full view's tap toggles tapped and it adds details and footer actions; the viewer's tap closes and it adds the rulings link and a caption with name, position and Flip; its own styles size the picture to the card, so those sit right under it). Rule: the frame holds only what every screen has; anything one screen needs stays in that screen, and a second one-screen option is the signal to split the frame again.
- **Pass turn (one device):** after `passTurn` is sent the screen blinds (`viewer` = `'nobody'`), as Blind my hand does.
- **Combat (one device):** `startCombat` (the Combat button, and Block in the full view) blinds first if a hand is showing, then enters combat mode. Marks made while blinded are the table's, so their changed borders count for the active player.
- **Slot taps in every mode:** `slotTap` handles a tap on a slot itself (its empty part or its open/close strip), opening or closing it, and a tap on a card in a collapsed row, which only opens the row. Normal, combat and attach modes all call it first, so their card taps act only in rows that are open or not crowded. The browser scenarios do the same through `inOpenRow` (open, act, close).
- **Stack order:** a drop on a pile goes to index 0, so the Stack's zone order is newest first. The Stack pile (`Pile` with `all`) draws every item, stacked under the top one, so the full view can hand any of them to a board drag; a tap on it opens the full view (see Stack and abilities), whose caption gives each item's position.
- **Tap:** attach mode, then combat mode, then pointer mode take a tap first. Otherwise a token tap creates nothing and shows a hint to drag it (tokens are created only by dragging), and a card tap follows the PRD's table (a tucked strip in a row that isn't fanned means its host).
- **Long-press:** opens the full view if the viewer can see the face, with `anchor` = that card. The row is `fullRowOf(state, anchor)`: for a battlefield card, `group` = its host then the host's attachments (closest first), and `partners` = the host's blockers (cards whose `blocking` includes it) if the host is attacking, else the attacking cards in the host's `blocking`; `role` is `attacker`, `blocker` or null. Picking a thumbnail changes `cardId` and keeps `anchor`, so the row stays fixed; if the shown card leaves the row, the row is rebuilt from it. No row is shown with fewer than two cards. Thumbnails show ⚔n / 🛡, the counter total, and for partners a gold "+N" attachment count; a divider separates group and partners. Marks and counters render in `.full-badges` under the image (inside `.fullcard-main`, a column), never over it; in portrait the card, strip and caption stack, in landscape the caption sits beside them.
- **Slot steps:** `slotSteps(state, cardId, zone, viewer, sheet)` lists the slot's cards in board order, each group once by its host, keeping only cards the viewer can see (in a peek, reveal, search or inspect tray, the tray's cards), and returns the neighbours of the shown card's host. A step always lands on a host (the group's lead), even when the shown card is an attachment. A 50 px mostly sideways swipe on `.fullcard-inner` sets `full` to that neighbour with `anchor` = it; ArrowLeft and ArrowRight do the same through one window listener that reads the latest targets from a ref. The ← and → are `aria-hidden` signs with `pointer-events: none`, hidden when there is no neighbour.
- **Drag up out of the full view:** `.fullcard-inner` has `touch-action: none` and its own pointer handlers. A move of more than 40 px up (and 1.5× more vertical than sideways) closes the full view and calls `adopt(el, pointerId, x0, y0, x, y)` on the gesture module (`attachGestures` returns `{ detach, adopt }`), with `el` the board's (or open tray's) element for the shown card. `adopt` checks `canDrag`, then starts an ordinary drag of that element; the usual host redirect makes it the whole group, and the rest of the gesture (ghost, hover, drop) runs as for a drag that began on the board.
- **Swipe down in the full view:** a release more than 50 px below the press (and 1.5× more vertical than sideways) calls `closeFull`, the same as Close.
- **Tap in the full view:** a release within 8 px of the press, on a card in battlefield or lands, sends `tap` (the card's tapped state flips). The full view never rotates the picture; a tapped card in play gets a `.badge.tap` ("↷ Tapped") first in `.full-badges`.
- **Two-finger spread:** the gesture module tracks every touch pointer. A second finger down ends the first finger's gesture (no tap, drag or long-press) and starts a spread, remembering the card the first finger was on (else the card under the midpoint) and its row. Once the fingers are 1.3× and at least 30 px farther apart, `onSpread(card, row)` fires once; the click that follows is swallowed. `Game` opens the full view through `onLongPress`: for a row with `data-collapsed`, on the lead card of the zone's first card; otherwise on the card. It does nothing while the full view or a sheet is open.
- **Matchup highlight:** closing the full view with **Close** sets the highlight to `anchor` if `matchupIds(state, anchor)` is non-empty. `matchupIds` takes the host, its attackers (itself if attacking, else the attackers it blocks), every card blocking those attackers, and all their attachments. Each render recomputes the set; the board gets `matching` and those cards `in-match` (outlined), and other cards in battlefield and lands rows dim to 38% opacity. A tap on anything that is not a card clears it, as does **Clear highlight**; when combat ends the set is empty, so it disappears.
- **Drop rules:** counters and marks dropped off their card are removed (in the full view any drag removes one); the Attack tag requires the active player's side; tokens are created at the drop index; cards move, and a drag that starts on an attached card drags its host, so the whole group moves (only Detach splits a group).
- **Combat mode:** a tap on the life counters opens them as in normal mode (combat damage changes life). Otherwise a tap on the active player's side toggles attacking, or completes a pending block when that card is attacking; a tap on the other side picks or unpicks the pending blocker. **End combat** asks `confirmBox({ title: 'End combat?', body: 'This clears <n> attacker(s) and <m> block(s).', ok: 'Clear marks', cancel: 'Keep fighting' })` (blocks counted per pairing) when any mark exists, then sends `endCombat`.
- **Alerts:** in two-device games, alerts from the other player and all dice results show as toasts. On one device, every ticker line (commands and notices except `point`) is kept with its actor and alert flag; unblinding to a player shows the lines by anyone else since that player last looked as "While \<name> was away", alerts highlighted.
- **Pointer:** the ring is drawn around the card, or else its slot, for 3 s in the pointer's colour.
- **Other:** the screen wake lock is requested during play and re-requested when the page becomes visible. A guest that isn't connected is shown greyed.
- **Sheets** (`Overlays.tsx`) cover the top 36–44% of the board: zone viewer (with Random card), peek, reveal, search and inspect trays, Player counters, Recent actions (with Export log), Tokens, Dice and random, Menu, While you were away, Re-pair.

## Stack and abilities

Status: built (steps 1 to 4: card text and rulings; abilities and ability items; the full view's model and the stack in the full view; the rulings panel). The stack becomes a place both players manage: spells and abilities go on it, both players see them in order, and they resolve one at a time. The app stays a playmat: it does not enforce timing or priority, and every default can be overridden or undone.

**Build order.** (1) Card text and rulings from Scryfall. (2) Abilities listed in the full view, a tap putting one on the stack as an ability item (`putAbility`, the item deleted when it leaves the stack, drawn on the board). (3) The full view's model (`fullModel`) and the stack in the full view. (4) The rulings panel. Each step ships and is tested on its own. Putting an ability on the stack needs the item, so the item came forward from step 3 into step 2.

**1. Card text.** Import also keeps, for each card and each face (`card_faces` for double-faced and split cards): `oracle_text`, `type_line`, `mana_cost`, `power`, `toughness`, `loyalty`, `defense`. They are stored on the card definition beside the images, as typed fields the code reads, together with the rest of Scryfall's card record (minus prices, purchase and page links) kept as delivered for later use: oracle id, keywords, mana value, colours, colour identity, produced mana, layout, related cards, rarity, set, collector number, artist. Existing card data is dropped rather than migrated: a schema bump clears stored definitions, and decks are re-imported (the built-in starter packs download again with one tap). Sample cards have no text. Scryfall has no structured list of abilities: its `oracle_text` is one string whose paragraphs are separated by `\n` (Scryfall: "only the \n character for newlines"), so abilities are derived from it (below).

**Rulings.** Import also fetches each card's rulings (`GET /cards/{set}/{number}/rulings`; Wizards' rulings and release notes marked `wotc`, Scryfall's own notes marked `scryfall`), stored once per oracle id in their own store, so every printing shares them. Basic lands are skipped. A failed rulings request leaves that card without rulings and never fails the import. Estimated cost: 0.5–2 KB and one request (120 ms apart) per unique card.

**One request per unique card, across a batch.** Images were already reused across decks (any card stored with all three sizes is not downloaded again). Lookups are now shared too: importing several decks at once (a starter pack, a Jumpstart selection) passes one lookup cache through the batch, so a card name or a token id is requested at most once per batch; rules text and rulings follow the images' rule, fetched only for cards not yet on the device.

**The rulings panel (built in step 4).** In the full view, a card with rulings shows one line, "Rulings (3)", just under its name, where it shows without scrolling on a phone held upright (no footer button). A tap opens a panel over the full view: the card's name, type line and rules text for each face at the top, then each ruling with its date, Scryfall's notes marked "Scryfall note (unofficial)". It scrolls, and **Back** or a swipe down on its header returns to the full view (Back, not Close: the footer's Close closes the whole full view). The rulings come from the `rulings` store by the card's oracle id (`useRulings` and `RulingsPanel` in `Rulings.tsx`); an ability item shows its source's. Stepping to another card closes the panel. The card viewer (deck page, Tokens sheet) shows the same link in its caption and the same panel, and its Escape closes the panel before the viewer. One behaviour on every device: the full view's details area is too small on a phone to unfold several rulings in place.

**2. Abilities in the full view.** A card's abilities are its Oracle paragraphs, for the face currently up, with two joins: a line starting with "•" belongs to the paragraph above it (modal "Choose one —" abilities), and that is all; reminder text stays with its line, and a keyword line ("Flying, vigilance") stays one line. The app does not classify lines (activated, triggered, static): every line is offered, and the player chooses. The full view lists them beside the card (below it on a phone held upright, where the list scrolls). To put one on the stack, drag it sideways out of the list: the full view closes with the line under the finger, and dropped on the Stack pile it goes on top; dropped anywhere else, nothing happens. A tap does nothing, so an ability is never added by mistake, and an up or down swipe on the list still scrolls it (the lines are `touch-action: pan-y`). A last line, **Custom…**, is a tap: it asks for any text (a delayed trigger, an effect from elsewhere), and the dialog's Put on stack button is the confirmation. Offered only for cards whose face the viewer can see, in any zone but the stack (a card in hand, for cycling). A card already on the stack shows no list: its rare cast triggers (cascade, storm, "when you cast") go on through Custom… on any card. A card with no stored text (sample cards) offers only Custom…. The parser is `abilityLines` and `abilitiesOf` in `ui/abilities.ts`; the text comes from the card definition through `Art.text`.

**Ability items (built in step 2).** An ability on the stack is stored like a card in the `stack` zone, so zone order, numbering, undo, sync and the full view's slot steps all apply unchanged. Its `CardInstance` (id `a<n>`) carries `ability: { text, sourceId }`, and takes the source's `defId` (its picture), name, deckId and owner when it is put on the stack, so the item still shows where it came from if the source dies in response or was a token that has vanished. Like a token, an ability item is deleted when it leaves the stack. New command `putAbility { cardId, from, text }` (protocol 5; `cardId` is the source, so it shares the other commands' location check and marking); it is a marking command, so a source in play gets a changed border. An ability of a face-down source is itself face down: its owner sees the picture, the other player sees the card back and "Ability of a face-down card", and both see the text. In the full view an item shows "Ability of" with the source's name, then its text, and offers no abilities of its own; on the board it is the source's picture with an "Ability" band and the text. The log names the source only when both players could see it.

**The full view reads a model (built in step 3).** `fullModel(state, cardId, zone, viewer)` in `ui/fullModel.ts` returns what the view and its footer need: the card and zone, whether the viewer sees the face, the title ("Hidden card", "Ability of" and the source's name), an ability item's text, the stack caption, whether to offer abilities (not on the stack), whether a tap toggles tapped, and the footer's actions (flip, face down, reveal, tap, attack, block, attach, detach, make lead, detach all, counters). `FullCard` and the footer read the model instead of testing kinds. The subject is a card id: an ability item is a card on the stack, so its kind comes from `card.ability` and no separate subject type is needed. For an ability item: no footer actions but Close, no counters, no tap toggle; swiping still steps through the stack, and drag up carries the item itself (never its source card); dropping it on any slot off the stack removes it, which is how an ability resolves. No footer button is added.

**The stack in the full view (built in step 3).** A tap on the Stack pile opens the full view on its top item (an empty stack does nothing), replacing the stack's card-row sheet and its numbering. The view's caption shows "Stack 1 of 3 · resolves first" for the top item and "Stack 2 of 3" below it. Every item counts in the steps and the caption, hidden or not; a hidden one shows the card back. Swipes step down the stack; drag up carries a card to any slot (a countered spell to the graveyard, say); swipe down closes. Resolving is explicit, by dragging: a spell is dragged to where it goes (a creature to the battlefield, an instant to the graveyard), and an ability item is dragged off the stack, which removes it. The app does not move cards by type line, and adds no footer button. Any item may be resolved, not only the top. Reordering a stack in place is not supported (drag a card back onto the pile to put it on top). On the board, the Stack pile shows an ability item as its source's picture with an "ability" band and the text.

**Resolving together.** Some tables play every spell onto the stack first, then look together and resolve. The app supports this without a setting: the player taps **Blind my hand** when done adding (holding priority to add more, or to respond to one's own spell, is normal play, so the app does not blind on each addition). Lands and mana abilities do not use the stack, as in the rules.

**Tests.** Unit: paragraph splitting and joins on real Oracle texts (modal, keywords, reminder text, double-faced faces); `putAbility` and deletion on leaving the stack; an ability item deleted when moved off the stack; `fullModel` for each subject kind. Browser: put an ability on the stack from the full view; step through a mixed stack; drag up an ability off the stack (removed, its source unmoved) and a creature onto the battlefield; drag up a spell to the graveyard; the face-down case.

**Decided.** No Resolve button and no moves by type line: resolving is done by dragging. No automatic blind on stack additions. The "Stack 1 of 3" caption shows only for stack items, so it also signals that the players are looking at the stack.

## Replacing v1

The app isn't in production, so v2 replaces v1 outright: nothing on a device carries over, and there is no upgrade path from an installed v1 app.

- **The site** serves nothing from the moment v1's code leaves `main` until v2 first deploys. An installed v1 app may keep running from its own cached copy meanwhile; that isn't guaranteed and doesn't matter.
- **Each device, once v2 is live:** remove the installed app and clear the site's data (in the browser's site settings for `pikalaw.github.io`), open https://pikalaw.github.io/travel-tabletop/, install it again, and re-import decks. Clearing the data matters: the v1 worker would otherwise keep serving v1.
- **Not supported:** pairing a v1 device with a v2 device (`APP_VERSION` becomes `0.2.0`, and the handshake refuses a different version as before), carrying saved games across, and going back to v1 other than by checking out the `v1` tag.
